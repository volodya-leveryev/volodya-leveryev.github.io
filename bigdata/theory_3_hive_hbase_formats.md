# Неделя 3. Hive, HBase, форматы хранения данных

## Apache Hive

### Зачем нужен Hive

MapReduce требует написания Java-кода для каждого запроса к данным, что неудобно для аналитиков. **Apache Hive** решает эту проблему: он позволяет писать SQL-подобные запросы (**HiveQL**), которые транслируются в задания MapReduce, Tez или Spark и выполняются над данными, лежащими в HDFS (или объектном хранилище).

Важно понимать: Hive — это не СУБД в классическом смысле. Это движок трансляции запросов и слой метаданных поверх файлов. Сами данные как лежали файлами (CSV, Parquet и т.д.) в HDFS, так там и остаются.

### Архитектура Hive

* **Driver** — принимает запрос, управляет жизненным циклом его выполнения (компиляция, оптимизация, выполнение)
* **Compiler** — разбирает HiveQL, строит план выполнения (DAG заданий)
* **Metastore** — хранилище метаданных: какие есть базы данных, таблицы, их схемы, партиции, расположение файлов на HDFS
* **Execution Engine** — фактически выполняет план на кластере; исторически это был MapReduce, сейчас чаще используются **Tez** или **Spark** (значительно быстрее на итеративных и многошаговых запросах)

### Metastore подробнее

Metastore — ключевой компонент, который отличает Hive от простого чтения файлов вручную. Он хранит:

* схемы таблиц (имена и типы колонок)
* информацию о партициях и их физическом расположении в HDFS
* формат хранения данных и сериализатор (SerDe)
* права доступа и статистику для оптимизатора запросов

По умолчанию Hive использует встроенную БД **Derby** для metastore — она подходит только для локальных экспериментов (не поддерживает несколько одновременных подключений). В продуктивных кластерах metastore выносят во внешнюю реляционную СУБД (**MySQL** или **PostgreSQL**), чтобы несколько пользователей и сервисов (Hive, Spark, Presto/Trino) могли обращаться к одному и тому же каталогу таблиц одновременно.

### HiveQL: основы

HiveQL синтаксически похож на стандартный SQL, но есть принципиальные отличия:

| SQL (реляционная СУБД) | HiveQL |
|---|---|
| Данные меняются построчно (UPDATE/DELETE эффективны) | Данные оптимизированы под запись большими порциями, точечные UPDATE/DELETE исторически не поддерживались (в новых версиях — ограниченно, через ACID-таблицы) |
| Индексы по умолчанию | Оптимизация через партиционирование/бакетирование, а не B-tree индексы |
| Мгновенный отклик (мс) | Задержка от секунд до минут — даже простой запрос компилируется в распределенное задание |
| Схема жестко проверяется при записи | Часто применяется schema-on-read: файлы уже лежат в HDFS, а схема "накладывается" при чтении |

Базовые команды:

```sql
-- Создание базы данных
CREATE DATABASE IF NOT EXISTS sales;
USE sales;

-- Создание таблицы (managed / internal table)
CREATE TABLE orders (
    order_id     BIGINT,
    customer_id  BIGINT,
    amount       DECIMAL(10,2),
    status       STRING
)
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ','
STORED AS TEXTFILE;

-- Внешняя таблица (external table) — Hive не управляет жизненным циклом файлов
CREATE EXTERNAL TABLE orders_ext (
    order_id     BIGINT,
    customer_id  BIGINT,
    amount       DECIMAL(10,2),
    status       STRING
)
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ','
LOCATION '/data/sales/orders/';
```

**Managed (internal) table** — Hive владеет данными: при `DROP TABLE` файлы в HDFS удаляются вместе с метаданными.
**External table** — Hive хранит только метаданные и ссылку на расположение файлов: при `DROP TABLE` удаляются только метаданные, файлы остаются нетронутыми. Внешние таблицы обычно используют, когда с одними и теми же файлами работают несколько систем (например, и Hive, и Spark).

### Партиционирование (Partitioning)

**Партиционирование** — это разбиение таблицы на физически отдельные каталоги в HDFS по значению одной или нескольких колонок (чаще всего — по дате). Это позволяет запросу читать не всю таблицу целиком, а только нужные каталоги (**partition pruning**), что резко ускоряет выполнение на больших таблицах.

```sql
-- Партиционированная таблица (партиция по дате и стране)
CREATE TABLE orders_partitioned (
    order_id     BIGINT,
    customer_id  BIGINT,
    amount       DECIMAL(10,2),
    status       STRING
)
PARTITIONED BY (order_date STRING, country STRING)
STORED AS PARQUET;
```

Физически на HDFS это будет выглядеть так:

```
/user/hive/warehouse/sales.db/orders_partitioned/order_date=2026-09-01/country=RU/
/user/hive/warehouse/sales.db/orders_partitioned/order_date=2026-09-01/country=DE/
/user/hive/warehouse/sales.db/orders_partitioned/order_date=2026-09-02/country=RU/
```

Запрос `WHERE order_date = '2026-09-01'` прочитает только каталог с этой датой, полностью проигнорировав остальные — это и есть суть partition pruning.

**Статическое партиционирование** — значение партиции указывается явно при загрузке данных:

```sql
INSERT INTO TABLE orders_partitioned PARTITION (order_date='2026-09-01', country='RU')
SELECT order_id, customer_id, amount, status FROM orders_ext
WHERE order_date = '2026-09-01' AND country = 'RU';
```

**Динамическое партиционирование** — Hive сам определяет значения партиций из данных:

```sql
SET hive.exec.dynamic.partition = true;
SET hive.exec.dynamic.partition.mode = nonstrict;

INSERT INTO TABLE orders_partitioned PARTITION (order_date, country)
SELECT order_id, customer_id, amount, status, order_date, country
FROM orders_ext;
```

**Подводный камень:** партиционирование по колонке с высокой кардинальностью (например, по `customer_id`) создаст миллионы мелких каталогов с крошечными файлами — это резко замедлит работу (проблема "small files"), а не ускорит. Партиционировать стоит по колонкам с умеренным числом уникальных значений (дата, страна, категория).

### Бакетирование (Bucketing)

**Бакетирование** — разбиение данных внутри (партиции или всей таблицы) на фиксированное число файлов (бакетов) по хэшу значения колонки. В отличие от партиционирования, число бакетов задается заранее и не зависит от количества уникальных значений колонки — это решает проблему высокой кардинальности.

```sql
CREATE TABLE orders_bucketed (
    order_id     BIGINT,
    customer_id  BIGINT,
    amount       DECIMAL(10,2),
    status       STRING
)
CLUSTERED BY (customer_id) INTO 32 BUCKETS
STORED AS PARQUET;
```

Зачем это нужно:

* **Ускорение JOIN** — если две таблицы бакетированы по одной колонке с одинаковым числом бакетов, Hive может выполнить join бакет-к-бакету (**bucket map join**), не перемешивая все данные (без полного shuffle)
* **Эффективный sampling** — можно быстро выбрать репрезентативную выборку данных (`TABLESAMPLE(BUCKET 1 OUT OF 32)`), не читая всю таблицу

**Партиционирование vs Бакетирование — коротко:**

| | Партиционирование | Бакетирование |
|---|---|---|
| Единица разбиения | Каталог в HDFS | Файл внутри каталога |
| Число частей | Зависит от данных (кол-во уникальных значений) | Задается заранее, фиксировано |
| Подходит для | Колонок с низкой/умеренной кардинальностью (дата, регион) | Колонок с высокой кардинальностью (id пользователя) |
| Основной эффект | Partition pruning (пропуск ненужных каталогов) | Ускорение join, sampling |

Партиционирование и бакетирование можно комбинировать: партиционировать по дате, а внутри каждой партиции — бакетировать по `customer_id`.

## Apache HBase (кратко, для контраста с Hive)

**HBase** — распределенная колоночная (wide-column) NoSQL-СУБД, построенная поверх HDFS, вдохновленная Google Bigtable.

### Архитектура (в общих чертах)

* **HMaster** — управляет метаданными, распределением регионов между серверами
* **RegionServer** — обслуживает конкретные диапазоны строк таблицы (регионы), обрабатывает чтение/запись
* **Region** — таблица разбивается на регионы по диапазону ключей строк (rowkey), каждый регион хранится в виде **HFile** на HDFS
* Данные организованы в **column families** — группы колонок, физически хранящиеся вместе

Ключевая идея HBase: доступ к данным идет по **rowkey** — это единственный "индекс" в системе. Хорошо спроектированный rowkey (избегающий "горячих" регионов при последовательной записи) критичен для производительности.

### HBase vs Hive — главное отличие

Это не конкурирующие, а взаимодополняющие инструменты, решающие разные задачи:

| | Hive | HBase |
|---|---|---|
| Тип нагрузки | OLAP — аналитические batch-запросы к большим объемам | Похоже на OLTP — быстрый точечный доступ по ключу (чтение/запись отдельных записей) |
| Задержка | Секунды–минуты (даже простой запрос компилируется в job) | Миллисекунды (прямой доступ к региону по rowkey) |
| Модель данных | Таблицы со схемой, применяемой при чтении | Разреженная (sparse) таблица с column families, гибкая схема на уровне колонок |
| Типичный запрос | `SELECT ... GROUP BY ...` по миллиардам строк | `GET row_key` или `PUT row_key, value` — единичная запись |
| Аналогия | Хранилище данных (data warehouse) поверх файлов | NoSQL key-value / wide-column БД |

**Итог:** если нужно посчитать агрегаты по историческим данным — используем Hive; если нужен быстрый произвольный доступ к отдельным записям (например, профиль пользователя по его ID в реальном времени) — используем HBase.

## Форматы хранения: Parquet, ORC, Avro

Формат файлов, в котором физически лежат данные в HDFS/объектном хранилище, критично влияет на производительность и объем хранения. Все три формата поддерживают **эволюцию схемы** (schema evolution — добавление/изменение полей без переписывания старых файлов), но устроены и применяются по-разному.

### Строковое vs колоночное хранение

* **Строковое (row-oriented)** хранение — записи хранятся целиком, одна за другой. Хорошо подходит, когда нужно прочитать/записать всю строку целиком (например, при потоковой передаче событий).
* **Колоночное (columnar) хранение** — значения одной колонки хранятся вместе, отдельно от других колонок. Выгодно для аналитических запросов, которые обычно используют не все колонки таблицы, а лишь несколько — читаются только нужные колонки, а не вся строка целиком. Плюс однородные данные внутри колонки лучше сжимаются.

### Avro — строковый формат

* **Ориентация:** строковая (row-oriented)
* **Назначение:** сериализация данных для передачи и хранения, особенно в потоковых системах (Kafka часто использует Avro для сериализации сообщений)
* Схема хранится в формате JSON вместе с данными (или отдельно, в **Schema Registry**), что обеспечивает удобную и надежную эволюцию схемы (добавление полей с default-значениями, переименование через алиасы)
* Компактный бинарный формат, эффективен для записи
* Плохо подходит для аналитических запросов "прочитать одну колонку из миллиарда строк" — придется читать все строки целиком

### Parquet — колоночный формат

* **Ориентация:** колоночная
* Разработан Twitter и Cloudera, вдохновлен форматом Google Dremel
* Широкая экосистемная поддержка: Spark, Hive, BigQuery (external tables), Presto/Trino, Pandas — де-факто стандарт для аналитических данных в data lake
* Поддерживает **predicate pushdown** — фильтрация данных на уровне чтения файла (не нужно поднимать в память данные, не удовлетворяющие условию `WHERE`)
* Эффективное сжатие (Snappy, GZIP) за счет однородности данных в колонках
* Хранит статистику (min/max) по блокам данных, что дополнительно ускоряет фильтрацию

### ORC (Optimized Row Columnar) — колоночный формат

* **Ориентация:** колоночная
* Разработан внутри экосистемы Hadoop специально для оптимизации Hive
* Встроенные легковесные индексы внутри файла (min/max на уровне блоков, bloom-фильтры) — часто дает более быструю фильтрацию в Hive, чем Parquet
* Поддерживает ACID-транзакции в Hive (INSERT/UPDATE/DELETE на уровне строк) — эта возможность в Hive исторически завязана именно на ORC
* Как правило, лучше сжимается, чем Parquet, на однотипных данных, но: экосистемная поддержка вне Hadoop/Hive (Spark, BigQuery, Trino) исторически слабее, чем у Parquet

### Сравнительная таблица

| | Avro | Parquet | ORC |
|---|---|---|---|
| Ориентация | Строковая | Колоночная | Колоночная |
| Лучше всего для | Передача данных, потоковая обработка, сериализация сообщений (Kafka) | Аналитика в общем data lake, максимальная кроссплатформенность | Аналитика внутри Hive, ACID-транзакции в Hive |
| Экосистема | Kafka, Spark, Hive | Spark, Hive, BigQuery, Trino, Pandas (почти везде) | В первую очередь Hive; поддержка в Spark/Trino есть, но менее развита |
| Эволюция схемы | Отличная (явная схема + Schema Registry) | Хорошая | Хорошая |
| Сжатие | Среднее | Хорошее | Как правило, лучшее на однородных данных |
| Predicate pushdown | Нет (нужно читать всю строку) | Да | Да, плюс встроенные индексы/bloom-фильтры |

**Практическое правило:** если данные "летят" через систему (события, сообщения из Kafka) — Avro. Если данные лежат в data lake и читаются множеством разных движков — Parquet (безопасный дефолтный выбор). Если экосистема целиком построена вокруг Hive и нужны ACID-таблицы — ORC.

## Практика

### Подготовка

Работа предполагается в среде с установленным Hive (например, через Docker-контейнер с Hadoop + Hive, или на облачном кластере — AWS EMR / GCP Dataproc). Понадобится доступ к Hive CLI/Beeline и HDFS.

В качестве учебного датасета удобно взять что-то вроде публичного датасета поездок такси NYC (NYC Taxi Trips) или логов интернет-магазина — большого объема, с колонкой даты для партиционирования и колонкой с высокой кардинальностью (id клиента/водителя) для бакетирования.

### Шаг 1. Загрузка сырых данных в HDFS

```bash
# Копируем CSV-файл с локальной машины в HDFS
hdfs dfs -mkdir -p /data/raw/taxi_trips
hdfs dfs -put taxi_trips_2026.csv /data/raw/taxi_trips/
```

### Шаг 2. Создание внешней "сырой" таблицы

```sql
CREATE DATABASE IF NOT EXISTS taxi;
USE taxi;

CREATE EXTERNAL TABLE trips_raw (
    trip_id       BIGINT,
    pickup_ts     TIMESTAMP,
    dropoff_ts    TIMESTAMP,
    driver_id     BIGINT,
    passenger_count INT,
    trip_distance DOUBLE,
    fare_amount   DECIMAL(8,2),
    pickup_borough STRING
)
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ','
LOCATION '/data/raw/taxi_trips/'
TBLPROPERTIES ('skip.header.line.count'='1');
```

### Шаг 3. Проверка данных простыми запросами

```sql
SELECT COUNT(*) FROM trips_raw;

SELECT pickup_borough, COUNT(*) AS trips, AVG(fare_amount) AS avg_fare
FROM trips_raw
GROUP BY pickup_borough
ORDER BY trips DESC;
```

### Шаг 4. Создание партиционированной и бакетированной таблицы в Parquet

Партиционируем по дате поездки (низкая/умеренная кардинальность — удобно для partition pruning), бакетируем по `driver_id` (высокая кардинальность — не годится для партиционирования).

```sql
CREATE TABLE trips_optimized (
    trip_id       BIGINT,
    pickup_ts     TIMESTAMP,
    dropoff_ts    TIMESTAMP,
    driver_id     BIGINT,
    passenger_count INT,
    trip_distance DOUBLE,
    fare_amount   DECIMAL(8,2),
    pickup_borough STRING
)
PARTITIONED BY (pickup_date STRING)
CLUSTERED BY (driver_id) INTO 16 BUCKETS
STORED AS PARQUET;
```

### Шаг 5. Заполнение таблицы через динамическое партиционирование

```sql
SET hive.exec.dynamic.partition = true;
SET hive.exec.dynamic.partition.mode = nonstrict;
SET hive.enforce.bucketing = true;

INSERT OVERWRITE TABLE trips_optimized PARTITION (pickup_date)
SELECT
    trip_id,
    pickup_ts,
    dropoff_ts,
    driver_id,
    passenger_count,
    trip_distance,
    fare_amount,
    pickup_borough,
    DATE(pickup_ts) AS pickup_date
FROM trips_raw;
```

### Шаг 6. Проверка партиций

```sql
SHOW PARTITIONS trips_optimized;

-- Запрос, использующий partition pruning: читает только один каталог с датой
SELECT COUNT(*), AVG(fare_amount)
FROM trips_optimized
WHERE pickup_date = '2026-09-01';
```

Полезно сравнить план выполнения (`EXPLAIN`) этого запроса к `trips_raw` (сканирование всей таблицы) и к `trips_optimized` (сканирование одной партиции) — разница в объеме читаемых данных наглядно покажет эффект partition pruning.

### Шаг 7. Аналитические запросы HiveQL

```sql
-- Топ-10 самых загруженных районов по количеству поездок за месяц
SELECT pickup_borough, COUNT(*) AS trips_count
FROM trips_optimized
WHERE pickup_date BETWEEN '2026-09-01' AND '2026-09-30'
GROUP BY pickup_borough
ORDER BY trips_count DESC
LIMIT 10;

-- Оконная функция: ранжирование водителей по выручке внутри каждого дня
SELECT
    pickup_date,
    driver_id,
    SUM(fare_amount) AS daily_revenue,
    RANK() OVER (PARTITION BY pickup_date ORDER BY SUM(fare_amount) DESC) AS rnk
FROM trips_optimized
GROUP BY pickup_date, driver_id;

-- Пример bucket map join: соединение двух бакетированных по driver_id таблиц
-- (предполагается, что таблица drivers также CLUSTERED BY (driver_id) INTO 16 BUCKETS)
SET hive.optimize.bucketmapjoin = true;

SELECT t.driver_id, d.driver_name, COUNT(*) AS trips
FROM trips_optimized t
JOIN drivers d ON t.driver_id = d.driver_id
GROUP BY t.driver_id, d.driver_name;
```

### Шаг 8. Сравнение форматов на практике (опционально)

Для закрепления темы форматов хранения полезно создать одну и ту же таблицу в трех форматах и сравнить:

```sql
CREATE TABLE trips_avro   STORED AS AVRO    AS SELECT * FROM trips_raw;
CREATE TABLE trips_parquet STORED AS PARQUET AS SELECT * FROM trips_raw;
CREATE TABLE trips_orc    STORED AS ORC     AS SELECT * FROM trips_raw;
```

После этого сравнить:

* объем занимаемого места на HDFS (`hdfs dfs -du -h /user/hive/warehouse/taxi.db/`)
* время выполнения одинакового аналитического запроса (`GROUP BY` + `AVG`) к каждой из трех таблиц
* время выполнения запроса, выбирающего только одну-две колонки, — разница между Avro и колоночными форматами должна быть особенно заметна

### Задания для самостоятельной практики

1. Создать таблицу, партиционированную одновременно по дате и по borough (двухуровневое партиционирование), и сравнить размер и число партиций с однотуровневым вариантом.
2. Специально создать таблицу, партиционированную по `driver_id` (колонка с высокой кардинальностью), и убедиться на практике в проблеме "small files" (много мелких партиций/файлов, деградация производительности).
3. Написать запрос с `EXPLAIN` и сопоставить план выполнения для запроса к неоптимизированной (`trips_raw`, TEXTFILE) и оптимизированной (`trips_optimized`, Parquet + партиции + бакеты) таблице.
