# Неделя 4. Введение в Apache Spark

## Почему Spark быстрее MapReduce

### Проблема MapReduce

Классический MapReduce между каждым шагом вычислений (map → shuffle → reduce) обязан записывать промежуточные результаты на диск (в HDFS). Это дает надежность (можно восстановиться после сбоя узла), но для многошаговых и итеративных алгоритмов (например, join нескольких таблиц или обучение ML-модели, где нужно много раз пройти по одним и тем же данным) означает постоянные циклы "прочитать с диска → обработать → записать на диск" между каждой парой Map/Reduce заданий.

### In-memory computing

**Apache Spark** решает эту проблему, храня промежуточные результаты вычислений в оперативной памяти узлов кластера, а не на диске. Диск используется только для исходного чтения данных и финальной записи результата (а также когда данные не помещаются в память — тогда часть данных вытесняется на диск, но это исключение, а не норма). За счет этого многошаговые и итеративные вычисления (характерные для аналитики и машинного обучения) на Spark выполняются кратно быстрее, чем на классическом MapReduce — производители Spark в свое время заявляли об ускорении в 10–100 раз на подобных нагрузках.

Важная оговорка: это не значит, что Spark "магически" быстрее для абсолютно любой задачи — если задача состоит из одного простого map-прохода по данным без повторного к ним обращения, разница с MapReduce будет не столь драматична. Главный выигрыш Spark проявляется именно на сложных многошаговых конвейерах.

### DAG (Directed Acyclic Graph)

MapReduce жестко ограничен моделью "один Map + один Reduce" на одно задание — сложную логику приходится собирать из цепочки нескольких MapReduce-заданий, каждое из которых записывает результат на диск. Spark вместо этого строит **DAG** (направленный ациклический граф) вычислений: пользователь описывает цепочку трансформаций данных, а Spark самостоятельно строит граф зависимостей между ними и оптимизирует порядок и способ их выполнения (например, объединяя несколько трансформаций в один физический шаг — этот процесс называется **pipelining**).

DAG строится и оптимизируется **до** фактического запуска вычислений (это возможно благодаря ленивым вычислениям — см. раздел про RDD ниже), что дает Spark возможность применить оптимизации на уровне всего конвейера, а не одной пары map/reduce.

## Архитектура Spark

Spark-приложение выполняется в распределенной среде и состоит из нескольких ключевых компонентов:

* **Driver** — процесс, в котором выполняется код пользовательского приложения (main-функция). Driver создает `SparkContext`/`SparkSession`, строит DAG вычислений, разбивает его на задачи (tasks) и распределяет их между executor'ами. Driver также собирает результаты выполнения (например, при действиях типа `collect()`).
* **Cluster Manager** — внешний компонент, отвечающий за выделение ресурсов (CPU, память) под приложение на кластере. Может быть:
  * **Standalone** — встроенный простой менеджер ресурсов Spark
  * **YARN** — менеджер ресурсов Hadoop (частый выбор в связке Spark + Hadoop-кластер)
  * **Kubernetes** — запуск executor'ов как поды в Kubernetes-кластере
  * **Mesos** — менее распространен сегодня
* **Executor** — процесс, запускаемый на рабочих узлах кластера, который непосредственно выполняет задачи (tasks), хранит данные в памяти (кэш) и возвращает результаты Driver'у. Каждый executor обладает выделенным количеством CPU-ядер и памяти.

Схема взаимодействия: пользователь запускает приложение → Driver запрашивает у Cluster Manager ресурсы → Cluster Manager выделяет executor'ы на рабочих узлах → Driver распределяет задачи между executor'ами → executor'ы выполняют задачи и возвращают результаты.

Важно не путать **партиции данных** (units, на которые разбиты сами данные — см. ниже) и **executor'ы** (процессы, которые эти партиции обрабатывают): на одном executor'е может параллельно обрабатываться несколько партиций, если у него выделено несколько ядер.

## RDD (Resilient Distributed Dataset)

**RDD** — базовая абстракция данных в Spark: неизменяемая (immutable), распределенная по узлам кластера коллекция элементов, с которой можно работать параллельно.

Расшифровка названия отражает ключевые свойства:

* **Resilient** (устойчивый) — RDD способен восстановиться после потери части данных (например, при отказе узла), поскольку Spark хранит информацию о том, как эта RDD была получена (граф происхождения — **lineage**), и может пересчитать потерянную часть данных заново
* **Distributed** — данные физически разделены на партиции, размещенные на разных узлах кластера
* **Dataset** — коллекция данных (записи любого типа — не обязательно табличные строки)

### Создание RDD

RDD можно создать двумя основными способами:

```python
from pyspark import SparkContext

sc = SparkContext.getOrCreate()

# 1. Из коллекции в памяти driver'а (parallelize)
rdd_from_list = sc.parallelize([1, 2, 3, 4, 5], numSlices=4)

# 2. Из внешнего источника данных (файл, HDFS, S3 и т.д.)
rdd_from_file = sc.textFile("hdfs:///data/logs/access.log")
```

### Трансформации (Transformations) и действия (Actions)

Все операции над RDD делятся на два типа:

* **Трансформации** — создают новый RDD из существующего (`map`, `filter`, `flatMap`, `reduceByKey`, `join` и т.д.). Трансформации **ленивые** (см. ниже) — они не выполняются сразу.
* **Действия (Actions)** — запускают фактическое вычисление и возвращают результат driver'у или записывают его во внешнее хранилище (`collect`, `count`, `take`, `reduce`, `saveAsTextFile`).

```python
# Трансформации — вычисление НЕ запускается
words = rdd_from_file.flatMap(lambda line: line.split(" "))
pairs = words.map(lambda word: (word, 1))
word_counts = pairs.reduceByKey(lambda a, b: a + b)

# Действие — вот только теперь Spark реально выполнит весь граф вычислений
result = word_counts.collect()
```

### Ленивые вычисления (Lazy Evaluation)

Когда пользователь вызывает трансформацию (например, `map` или `filter`), Spark **не выполняет** вычисление немедленно — он лишь запоминает, что нужно сделать, добавляя новый узел в DAG. Реальное вычисление запускается только в момент вызова действия (action).

Зачем это нужно:

* Spark может увидеть весь граф вычислений целиком и **оптимизировать** его — например, объединить несколько последовательных `map`-операций в один физический проход по данным (не нужно на каждом шаге материализовывать промежуточный результат)
* Не выполняются вычисления, результат которых не понадобится (например, если часть графа не используется для получения финального результата)
* Позволяет эффективно работать с данными, которые не помещаются в память целиком — обработка идет потоково, партиция за партицией

Практическое следствие: если код с трансформациями "выполняется мгновенно", а затем реальная работа происходит только на вызове `.collect()` или `.count()` — это ожидаемое поведение, а не ошибка.

## Партиционирование данных и его влияние на производительность

Данные внутри RDD физически разбиты на **партиции** — минимальные единицы, которые обрабатываются параллельно одной задачей (task) на одном executor'е. Число и распределение партиций напрямую определяет степень параллелизма вычислений.

### Как определяется число партиций

* При чтении из файловой системы (HDFS/S3) число партиций обычно соответствует числу блоков файла (или задается явно)
* При `parallelize()` число партиций можно задать явно (`numSlices`)
* Операции, требующие перемешивания данных (shuffle) — например, `reduceByKey`, `join`, `groupByKey` — могут изменить число партиций (управляется параметром `spark.default.parallelism` или явным указанием, например `repartition(n)`)

### Влияние на производительность

* **Слишком мало партиций** относительно числа доступных ядер кластера — часть ресурсов кластера останется незагруженной, параллелизм не используется полностью
* **Слишком много мелких партиций** — накладные расходы на планирование и запуск множества мелких задач начинают превышать выигрыш от параллелизма (аналог проблемы "small files", но на уровне вычислений, а не хранения)
* **Неравномерное распределение данных по партициям (data skew)** — если, например, при `groupByKey` по ключу большинство записей попадает в одну партицию, эта партиция станет "бутылочным горлышком": все остальные executor'ы уже закончили работу, а один продолжает обрабатывать огромную партицию

### Shuffle — самая дорогая операция

Операции, требующие **перегруппировки данных между партициями** (shuffle) — такие как `groupByKey`, `reduceByKey`, `join`, `distinct`, `repartition` — являются самыми дорогими в Spark: они требуют записи промежуточных данных на диск и передачи по сети между узлами кластера. Понимание того, какие операции вызывают shuffle, — ключ к написанию эффективного Spark-кода (эта тема будет подробно разобрана на неделе про tuning производительности).

Управление партиционированием:

```python
# Узнать текущее число партиций
rdd_from_file.getNumPartitions()

# Увеличить число партиций (всегда вызывает shuffle)
rdd_repartitioned = rdd_from_file.repartition(20)

# Уменьшить число партиций (может избежать полного shuffle — coalesce "склеивает" партиции на месте)
rdd_coalesced = rdd_from_file.coalesce(4)
```

`coalesce()` предпочтительнее `repartition()`, когда нужно именно **уменьшить** число партиций, так как он старается избежать полного перемешивания данных по сети.

## Практика

### Шаг 1. Установка PySpark

Наиболее простой способ для локальной разработки и учебных целей — установка через pip (Spark в этом случае запускается в **локальном режиме**, без отдельного кластера, эмулируя многопоточность на одной машине):

```bash
# Требуется предустановленная Java (JDK 8, 11 или 17 — в зависимости от версии Spark)
java -version

pip install pyspark --break-system-packages

# Проверка установки
pyspark --version
```

Для более полноценной работы (несколько узлов, YARN/Kubernetes) Spark разворачивается отдельно, скачиванием дистрибутива с сайта проекта или через Docker-образ (например, `bitnami/spark`) — но для знакомства с RDD API локальной установки через pip достаточно.

### Шаг 2. Создание SparkContext / SparkSession

```python
from pyspark.sql import SparkSession

spark = SparkSession.builder \
    .appName("intro-to-spark") \
    .master("local[*]") \
    .getOrCreate()

sc = spark.sparkContext
print(sc.version)
```

`master("local[*]")` означает запуск в локальном режиме с использованием всех доступных ядер процессора — удобно для обучения и разработки без реального кластера.

### Шаг 3. Первые операции с RDD

```python
# Создаем RDD из списка чисел
numbers = sc.parallelize(range(1, 21), numSlices=4)

print("Число партиций:", numbers.getNumPartitions())

# Трансформация: возводим каждое число в квадрат
squares = numbers.map(lambda x: x * x)

# Трансформация: оставляем только четные квадраты
even_squares = squares.filter(lambda x: x % 2 == 0)

# Действие: вычисляем результат и забираем его в driver
result = even_squares.collect()
print(result)

# Действие: подсчет количества элементов
print("Количество элементов:", even_squares.count())

# Действие: сумма всех элементов
total = even_squares.reduce(lambda a, b: a + b)
print("Сумма:", total)
```

### Шаг 4. Классический пример Word Count на RDD

```python
# Предположим, у нас есть текстовый файл с логами или книгой
text_rdd = sc.textFile("sample_text.txt")

word_counts = (
    text_rdd
    .flatMap(lambda line: line.lower().split())      # трансформация: строка -> слова
    .map(lambda word: (word.strip(".,!?"), 1))       # трансформация: слово -> (слово, 1)
    .reduceByKey(lambda a, b: a + b)                  # трансформация (с shuffle!)
)

# Действие: топ-10 самых частых слов
top_words = word_counts.takeOrdered(10, key=lambda pair: -pair[1])
for word, count in top_words:
    print(f"{word}: {count}")
```

Обратите внимание: до вызова `takeOrdered` (действие) ни одна строка кода фактически не выполнялась над данными — все предыдущие вызовы лишь строили DAG.

### Шаг 5. Наблюдение за ленивыми вычислениями и DAG

```python
import time

big_rdd = sc.parallelize(range(1, 10_000_000), numSlices=8)

start = time.time()
transformed = big_rdd.map(lambda x: x * 2).filter(lambda x: x % 3 == 0)
print("Время на определение трансформаций:", time.time() - start)  # почти мгновенно

start = time.time()
count = transformed.count()  # тут запускается реальное вычисление
print("Время на выполнение действия:", time.time() - start)
print("Результат:", count)
```

Дополнительно полезно открыть **Spark UI** (по умолчанию доступен на `http://localhost:4040` при локальном запуске) и посмотреть вкладку **Jobs/Stages** — там видно, как DAG трансформаций был разбит на stages, сколько партиций обрабатывалось и сколько времени заняла каждая задача.

### Шаг 6. Эксперимент с партиционированием

```python
data = sc.parallelize(range(1, 1_000_001), numSlices=2)
print("Начальное число партиций:", data.getNumPartitions())

# Увеличиваем число партиций
data_repartitioned = data.repartition(8)
print("После repartition:", data_repartitioned.getNumPartitions())

# Сравниваем время выполнения одной и той же операции
import time

start = time.time()
data.map(lambda x: x ** 2).sum()
print("2 партиции:", time.time() - start)

start = time.time()
data_repartitioned.map(lambda x: x ** 2).sum()
print("8 партиций:", time.time() - start)
```

На локальной машине с несколькими ядрами версия с большим числом партиций (при условии, что число партиций не превышает число ядер намного) обычно будет выполняться быстрее — параллелизм используется полнее.
