# Systemd и управление службами в Linux

## 1. Система инициализации Linux

### 1.1. Назначение системы инициализации

- После загрузки ядра Linux необходимо запустить пользовательское пространство (userspace).
- Первым процессом пользовательского пространства традиционно становится процесс с PID 1.
- Основные задачи системы инициализации:
  - запуск системных служб и фоновых процессов;
  - управление зависимостями между службами;
  - организация последовательности запуска компонентов ОС;
  - контроль состояния служб;
  - обработка системных событий;
  - завершение работы ОС.

**Systemd** — система инициализации и менеджер служб Linux, используемый во многих современных дистрибутивах.

Особенности systemd:

- параллельный запуск служб с учётом зависимостей;
- декларативное описание конфигурации служб;
- централизованное управление службами;
- интеграция с журналированием;
- управление точками монтирования, устройствами, таймерами и другими ресурсами;
- возможность автоматического перезапуска служб.

### 1.2. Архитектура загрузки Linux

Упрощённая последовательность загрузки:

**BIOS / UEFI**

Инициализация оборудования

**Загрузчик (GRUB)**

Загрузка ядра и initramfs

**Ядро Linux**

Инициализация ядра и оборудования

**systemd (PID 1)**

Запуск служб и целевых состояний

**Пользовательское пространство**

Службы, процессы, пользовательские сеансы

Проверка процесса PID 1:

```
ps -p 1 -o pid,comm,args
```

Проверка используемой системы инициализации:

```
systemctl --version
```

## 2. Основные компоненты systemd

### 2.1. Unit — базовая единица управления

Unit — объект systemd, описывающий управляемый ресурс или действие.

| Тип unit     | Назначение                                |
| ------------ | ----------------------------------------- |
| `.service`   | Системная или пользовательская служба     |
| `.target`    | Группа units, целевое состояние системы   |
| `.socket`    | Активация службы через сокет              |
| `.mount`     | Точка монтирования файловой системы       |
| `.automount` | Автоматическое монтирование               |
| `.timer`     | Запуск действий по расписанию             |
| `.device`    | Устройство ядра                           |
| `.path`      | Активация при изменении файловой системы  |
| `.slice`     | Группа процессов для управления ресурсами |
| `.scope`     | Группа процессов, созданная вне systemd   |

### 2.2. Файлы конфигурации

- Unit-файлы описывают параметры управляемых объектов.
- Используется текстовый формат с секциями и параметрами.
- Типичные расположения:
  - `/usr/lib/systemd/system/` — системные unit-файлы, устанавливаемые пакетами (в некоторых дистрибутивах `/lib/systemd/system/`);
  - `/etc/systemd/system/` — локальные конфигурации администратора;
  - `~/.config/systemd/user/` — пользовательские службы.

Порядок поиска и приоритет конфигураций зависят от типа unit и механизма переопределения.

### 2.3. Целевые состояния (targets)

Target объединяет несколько units и задаёт определённое состояние системы.

Основные targets:

| Target              | Назначение                                           |
| ------------------- | ---------------------------------------------------- |
| `poweroff.target`   | Выключение системы                                   |
| `rescue.target`     | Режим восстановления                                 |
| `multi-user.target` | Многопользовательский режим без графической оболочки |
| `graphical.target`  | Многопользовательский режим с графической оболочкой  |
| `reboot.target`     | Перезагрузка                                         |

Просмотр текущего целевого состояния:

```
systemctl get-default
```

Установка целевого состояния по умолчанию:

```
sudo systemctl set-default multi-user.target
```

Переход в другое состояние без перезагрузки:

```
sudo systemctl isolate multi-user.target
```

## 3. Управление службами с помощью systemctl

`systemctl` — основная утилита взаимодействия с менеджером systemd.

### 3.1. Основные команды

| Команда                               | Назначение                                 |
| ------------------------------------- | ------------------------------------------ |
| `systemctl status nginx`              | Состояние службы                           |
| `systemctl start nginx`               | Запуск службы                              |
| `systemctl stop nginx`                | Остановка службы                           |
| `systemctl restart nginx`             | Перезапуск службы                          |
| `systemctl reload nginx`              | Перечитывание конфигурации службой         |
| `systemctl enable nginx`              | Автозапуск при загрузке                    |
| `systemctl disable nginx`             | Отключение автозапуска                     |
| `systemctl enable --now nginx`        | Включение автозапуска и немедленный запуск |
| `systemctl is-active nginx`           | Проверка активности                        |
| `systemctl is-enabled nginx`          | Проверка автозапуска                       |
| `systemctl list-units --type=service` | Список загруженных служб                   |

**Важно различать:**

- `start` — запуск службы сейчас;
- `enable` — настройка запуска при загрузке;
- `disable` — отключение автозапуска;
- `stop` — остановка работающей службы;
- `mask` — запрет запуска службы, в том числе через зависимости.

### 3.2. Просмотр зависимостей

```
systemctl list-dependencies nginx
```

Просмотр зависимостей для целевого состояния:

```
systemctl list-dependencies multi-user.target
```

Основные директивы зависимостей:

- `Requires=` — обязательная зависимость;
- `Wants=` — необязательная зависимость;
- `After=` — запуск после указанного unit;
- `Before=` — запуск до указанного unit;
- `Conflicts=` — несовместимые units.

**Принципиальный момент:** `After=` задаёт порядок запуска, но само по себе не запускает зависимую службу. Для задания зависимости используются `Requires=` или `Wants=`.

## 4. Создание собственной службы systemd

Практический пример

Рассмотрим создание службы, которая периодически записывает диагностическое сообщение в системный журнал.

**Задача:** реализовать фоновый процесс, который:

- запускается автоматически при загрузке ОС;
- выполняется от имени отдельного пользователя;
- каждые 10 секунд записывает сообщение;
- автоматически перезапускается при аварийном завершении;
- управляется через `systemctl`.

### 4.1. Создание программы

Создадим отдельного системного пользователя:

```
sudo useradd --system --no-create-home \
  --shell /usr/sbin/nologin demo-service
```

Создадим каталог и скрипт:

```
sudo mkdir -p /opt/demo-service
sudo nano /opt/demo-service/worker.sh
```

Содержимое скрипта:

```
#!/bin/bash

while true
do
    echo "Demo service is running: $(date)"
    sleep 10
done
```

Назначим права:

```
sudo chmod 755 /opt/demo-service/worker.sh
```

### 4.2. Создание unit-файла

Создадим файл:

```
sudo nano /etc/systemd/system/demo-service.service
```

Содержимое:

```
[Unit]
Description=Demo Background Service
After=multi-user.target

[Service]
Type=simple
User=demo-service
ExecStart=/opt/demo-service/worker.sh

Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

### 4.3. Разбор конфигурации

Unit-файл состоит из трёх основных секций.

**Секция&#x20;**`[Unit]`**&#x20;— общая информация**

| Директива      | Назначение                                |
| -------------- | ----------------------------------------- |
| `Description=` | Описание службы                           |
| `After=`       | Порядок запуска относительно другого unit |
| `Requires=`    | Обязательная зависимость                  |
| `Wants=`       | Необязательная зависимость                |

**Секция&#x20;**`[Service]`**&#x20;— параметры выполнения**

| Директива           | Назначение                         |
| ------------------- | ---------------------------------- |
| `Type=`             | Тип запуска службы                 |
| `User=`             | Пользователь процесса              |
| `Group=`            | Группа процесса                    |
| `ExecStart=`        | Команда запуска                    |
| `ExecStop=`         | Команда остановки                  |
| `ExecReload=`       | Команда перечитывания конфигурации |
| `WorkingDirectory=` | Рабочий каталог                    |
| `Restart=`          | Политика перезапуска               |
| `RestartSec=`       | Задержка перед перезапуском        |
| `Environment=`      | Переменные окружения               |

**Секция&#x20;**`[Install]`**&#x20;— подключение службы**

| Директива     | Назначение                                               |
| ------------- | -------------------------------------------------------- |
| `WantedBy=`   | Целевое состояние, при котором служба должна запускаться |
| `RequiredBy=` | Целевое состояние с обязательной зависимостью            |

### 4.4. Типы служб

Директива `Type=` определяет, как systemd интерпретирует запуск процесса.

- `simple` — процесс запускается непосредственно; основной процесс службы соответствует `ExecStart=`.
- `exec` — systemd ожидает успешного выполнения системного вызова `execve()` перед фиксацией запуска.
- `forking` — программа самостоятельно переходит в фоновый режим посредством создания дочернего процесса.
- `oneshot` — команда выполняется однократно, после чего завершается.
- `notify` — программа сообщает systemd о готовности через механизм уведомлений.
- `idle` — запуск откладывается до завершения других задач диспетчера.

Для большинства современных приложений рекомендуется использовать `simple` или `exec`, если приложение не требует специального протокола готовности.

### 4.5. Регистрация и запуск службы

После создания unit-файла необходимо перечитать конфигурацию systemd:

```
sudo systemctl daemon-reload
```

Проверим конфигурацию:

```
sudo systemd-analyze verify \
  /etc/systemd/system/demo-service.service
```

Запустим службу:

```
sudo systemctl start demo-service
```

Проверим состояние:

```
systemctl status demo-service
```

Включим автоматический запуск:

```
sudo systemctl enable demo-service
```

Либо выполним обе операции одной командой:

```
sudo systemctl enable --now demo-service
```

### 4.6. Проверка работы

Проверка процесса:

```
ps aux | grep demo-service
```

Просмотр журнала:

```
journalctl -u demo-service
```

Наблюдение за журналом в реальном времени:

```
journalctl -u demo-service -f
```

Остановка и отключение:

```
sudo systemctl stop demo-service
sudo systemctl disable demo-service
```

### 4.7. Типичные ошибки при создании служб

- Не выполнен `daemon-reload` после изменения unit-файла.
- Неправильно указан путь в `ExecStart=`.
- Отсутствуют права на выполнение скрипта.
- Пользователь службы не имеет доступа к рабочим каталогам.
- Программа завершается сразу после запуска.
- Неправильно выбран `Type=`.
- Не учтены зависимости от других служб.
- Служба запускается, но не выполняет ожидаемую работу.

**Важное замечание:** `enable` не запускает службу немедленно, а `start` не включает её автозапуск. Для изменения конфигурации unit-файла используется `daemon-reload`, а не `reload`.

## 5. Журналирование: systemd-journald и journalctl

### 5.1. Назначение journald

`systemd-journald` — компонент systemd, отвечающий за сбор и хранение системных журналов.

Источники сообщений:

- ядро Linux;
- системные службы;
- пользовательские процессы;
- стандартные потоки `stdout` и `stderr`;
- сообщения системного журналирования syslog.

Особенности:

- структурированное хранение записей;
- временные метки;
- информация об источнике сообщения;
- фильтрация по службе, процессу, приоритету и времени;
- поддержка журналов нескольких загрузок ОС.

Журнал может храниться:

- временно — в `/run/log/journal/`;
- постоянно — в `/var/log/journal/`.

Наличие постоянного хранилища зависит от конфигурации и настроек системы.&#x20;

### 5.2. Основные команды journalctl

| Команда                           | Назначение                        |
| --------------------------------- | --------------------------------- |
| `journalctl`                      | Просмотр всего доступного журнала |
| `journalctl -b`                   | Записи текущей загрузки           |
| `journalctl -b -1`                | Записи предыдущей загрузки        |
| `journalctl -u nginx`             | Записи определённой службы        |
| `journalctl -f`                   | Наблюдение в реальном времени     |
| `journalctl -n 50`                | Последние 50 записей              |
| `journalctl -p err`               | Сообщения уровня error и выше     |
| `journalctl --since today`        | Записи с начала текущего дня      |
| `journalctl --since "1 hour ago"` | Записи за последний час           |
| `journalctl -k`                   | Сообщения ядра                    |
| `journalctl --disk-usage`         | Объём журнала на диске            |

Примеры для созданной службы:

```
journalctl -u demo-service -b
```

```
journalctl -u demo-service --since "10 minutes ago"
```

```
journalctl -u demo-service -f
```

Вывод без интерактивного просмотрщика:

```
journalctl -u demo-service --no-pager
```

### 5.3. Приоритеты сообщений

В journald используются уровни приоритетов syslog:

| Приоритет   | Назначение                          |
| ----------- | ----------------------------------- |
| 0 — emerg   | Аварийная ситуация                  |
| 1 — alert   | Требуется немедленное вмешательство |
| 2 — crit    | Критическая ошибка                  |
| 3 — err     | Ошибка                              |
| 4 — warning | Предупреждение                      |
| 5 — notice  | Важное уведомление                  |
| 6 — info    | Информационное сообщение            |
| 7 — debug   | Отладочное сообщение                |

Примеры:

```
journalctl -p warning
journalctl -p err -b
journalctl -u ssh -p err
```

### 5.4. Управление размером журнала

```
journalctl --disk-usage
```

Удаление старых записей по времени:

```
sudo journalctl --vacuum-time=7d
```

Ограничение занимаемого места:

```
sudo journalctl --vacuum-size=500M
```

Настройки journald находятся в:

```
/etc/systemd/journald.conf
```

**Учебный вывод:** журналирование позволяет не только узнать, работает ли служба, но и установить причину её отказа.

## 6. Смежные инструменты Linux для администрирования и диагностики

Systemd не заменяет стандартные инструменты Linux. Для полноценного анализа работы ОС необходимо использовать несколько групп утилит.

### 6.1. Процессы и ресурсы

| Инструмент | Назначение                              | Пример            |
| ---------- | --------------------------------------- | ----------------- |
| `ps`       | Просмотр процессов                      | `ps aux`          |
| `top`      | Мониторинг процессов в реальном времени | `top`             |
| `htop`     | Интерактивный мониторинг процессов      | `htop`            |
| `pgrep`    | Поиск процессов                         | `pgrep nginx`     |
| `kill`     | Отправка сигнала процессу               | `kill -TERM 1234` |

| `uptime`   | Время работы и средняя нагрузка         | `uptime`          |

**Практическая связь с systemd:**

```
systemctl status nginx
ps -ef | grep nginx
top
```

Позволяет сопоставить состояние службы и состояние её процессов.

### 6.2. Диагностика загрузки системы

`systemd-analyze` — инструмент анализа процесса загрузки и конфигурации systemd.

Основные команды:

```
systemd-analyze
```

Общее время загрузки системы.

```
systemd-analyze blame
```

Время запуска отдельных служб.

```
systemd-analyze critical-chain
```

Анализ критической цепочки загрузки.

```
systemd-analyze verify demo-service.service
```

Проверка unit-файла на ошибки.

```
systemd-analyze security demo-service.service
```

Оценка применённых механизмов изоляции и ограничений безопасности службы.

## 7. Таймеры systemd и традиционный cron

### 7.1. Назначение таймеров

`systemd.timer` позволяет запускать службы по расписанию или при наступлении определённого события.

Аналогичная задача традиционно решается с помощью `cron`.

Особенности systemd-timer:

- интеграция с systemd;
- журналирование результатов выполнения;
- управление зависимостями;
- возможность запуска пропущенной задачи после включения компьютера;
- единый механизм управления задачами и службами.

### 7.2. Сравнение cron и systemd.timer

| Критерий             | cron                   | systemd.timer                    |
| -------------------- | ---------------------- | -------------------------------- |
| Расписание           | Crontab                | Unit-файл                        |
| Журналирование       | Обычно отдельно        | Через journald                   |
| Зависимости          | Ограниченные           | Полноценные зависимости systemd  |
| Пропущенные запуски  | Обычно не восполняются | Поддерживается `Persistent=true` |
| Управление           | `crontab`              | `systemctl`                      |
| Интеграция с systemd | Нет                    | Да                               |

### 7.3. Пример создания таймера

Создадим службу:

`/etc/systemd/system/backup-demo.service`

```
[Unit]
Description=Demo Backup Task

[Service]
Type=oneshot
ExecStart=/usr/bin/touch /tmp/backup-demo.txt
```

Создадим таймер:

`/etc/systemd/system/backup-demo.timer`

```
[Unit]
Description=Run Demo Backup Every Minute

[Timer]
OnCalendar=*-*-* *:*:00
Persistent=true
Unit=backup-demo.service

[Install]
WantedBy=timers.target
```

Активируем таймер:

```
sudo systemctl daemon-reload
sudo systemctl enable --now backup-demo.timer
```

Проверим:

```
systemctl list-timers
```

Посмотрим результат выполнения:

```
systemctl status backup-demo.service
journalctl -u backup-demo.service
```

**Обратить внимание:**

- `.timer` определяет расписание;
- `.service` определяет выполняемую команду;
- `Persistent=true` позволяет выполнить пропущенный запуск календарного таймера после восстановления системы;
- `OnCalendar=` задаёт календарное расписание.

## 8. Безопасность системных служб

При создании собственных служб важно учитывать принцип минимальных привилегий.

Основные рекомендации:

1. Не запускать службы от `root`, если это не требуется.
2. Создавать отдельную системную учётную запись.
3. Ограничивать права доступа к файлам и каталогам.
4. Использовать механизмы изоляции systemd.
5. Контролировать доступ службы к файловой системе.
6. Ограничивать использование ресурсов.

Примеры дополнительных директив:

```
[Service]
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
```

Назначение:

- `NoNewPrivileges=` — запрещает получение дополнительных привилегий через механизмы повышения прав;
- `PrivateTmp=` — предоставляет службе отдельное пространство временных каталогов;
- `ProtectSystem=` — ограничивает запись в системные каталоги;
- `ProtectHome=` — ограничивает доступ к домашним каталогам.

Дополнительные ограничения необходимо подбирать с учётом требований конкретного приложения: чрезмерная изоляция может нарушить его работу.

## Итоги лекции

Основные положения, которые должны усвоить студенты:

- systemd — система инициализации и менеджер служб Linux;
- PID 1 отвечает за запуск и управление пользовательским пространством;
- unit — основная единица управления systemd;
- `systemctl` используется для управления службами и другими объектами;
- unit-файлы позволяют декларативно описывать параметры служб;
- `journalctl` обеспечивает централизованный доступ к системным журналам;
- `systemd-analyze` помогает исследовать загрузку и проверять конфигурацию;
- `systemd.timer` позволяет реализовать планировщик задач;
- безопасность служб обеспечивается в том числе разграничением привилегий и механизмами изоляции.
